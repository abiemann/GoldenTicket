# GoldenTicket implementation audit

> Historical record: the certificate and installed web-app approach described below was retired
> on September 21, 2026. Current multi-human options are HTTP **Quick play** and **PRACTICAL**
> laptop sharing. Use the [current setup](phone-setup.md) and
> [device acceptance plan](companion-device-evidence.md).

Audit date: September 11, 2026. Scope: source in `D:\Projects\GoldenTicket`, its tests and dependency
graph, compared with the complete [DESIGN](../DESIGN.md). Corrective edits were made in the same
workspace. This directory has no Git repository, so there is no commit/diff baseline identifier.

## Verdict

**The Windows C# application is not complete and does not yet satisfy the full design.** It is a
working implementation slice for digital game state, manual train placement, local heuristic AI,
encrypted event persistence, and a WPF laptop interface. Large requested product subsystems are
absent, including the camera, phone PWA, voice/story, and photographed save/rebuild feature.

This audit fixes concrete implementation defects and adds missing safety behavior in the existing
slice. It does not treat placeholder projects, a simulated camera, or passing rules tests as evidence
that the absent features are complete. The remaining work is in [TODO](../TODO.md).

Additional design differences:

- `Snapshot` stores fingerprints and version metadata, not the encrypted complete-state snapshots
  specified by §19. Restoration currently depends on replaying the complete journal. There are no
  migration backups, portable archives, named checkpoint retention, or correction/undo branches.
- The AI difficulty levels vary a heuristic. Challenging sampled lookahead and comparative strength
  evaluation from §15 remain unfinished. Decision cancellation and bounded waiting are now enforced.
- The desktop project uses `SelfContained=false`; it requires the Windows Desktop runtime. The
  offline installer, native ML/camera packaging, and license/asset inventory have not been produced.
- Rules safety pauses for pathological card supply are preserved; the UI cannot resolve them with
  an approved continuation policy. These are release blockers documented in the rules policy file.

an internet attack surface: no companion network server is implemented in this build.

The privacy boundary remains the design's local, cooperative-player boundary. Windows DPAPI protects
copied private payloads for the current user; it does not protect secrets from that Windows account,
a debugger, or a compromised process. Camera evidence continues to be rejected explicitly; it is
not converted into a manual approval behind the user's back.

## Save compatibility

New writes use store schema 2 and `sha256-v2:` state fingerprints. Known schema 1 saves remain
readable using the original `sha256:` algorithm and the two historical snapshot sequence
conventions. Their next successful command upgrades the metadata/hash in the same transaction.
Unrecognized versions or corrupt state stop restoration; no plaintext-encryption fallback exists.

The legacy hash retains its historical coverage limitations until a new write. The current shipped
manifest already uses the canonical card-kind order, so existing installed card identities are
unchanged. Full backups and general save migrations remain outstanding work.

## Validation evidence

Environment: Windows build 26200, x64, .NET SDK 10.0.401 and runtime 10.0.12. Automated checks run
against generated/test-only sessions, not the user's saved matches or physical board.

The baseline built and passed 91/91 tests when run under normal Windows user-profile access. Six
DPAPI tests initially failed inside the restricted execution profile; the unchanged baseline passed
outside that profile. Encryption was not weakened or skipped to obtain that result.

The final suite passed **173/173 tests**, with no skipped tests. The Release-configuration build
completed with zero errors and 97 test-analyzer warnings, all `xUnit1051` cancellation-token
recommendations. All 100 simulated games completed with invariants and replay equality intact.
The locked NuGet graph reported no known vulnerable dependencies from the configured advisory
feed; this is an advisory check, not a guarantee that no vulnerability exists.

Final build, test, locked-restore, simulator and advisory results are recorded in
[validation evidence](evidence/audit-2026-09-11/validation.md). The final test runner artifact is
[final-tests.trx](evidence/audit-2026-09-11/final-tests.trx).

The automated suite covers pure rules, properties, privacy projections, real encrypted SQLite
save/replay, corruption, race/failure injections, and headless desktop view models. Simulator runs
exercise all-computer games at two, three, four, and five seats with invariants and deterministic
replay checks. These simulations use the same production rules; they are not an independent physical
rules/data audit or evidence of opponent strength.

Not validated by this audit:

- A physical board/camera setup, printed marker accuracy, train recognition, CPU/GPU inference, jog
  recovery, full cleanup/reconstruction, or real power-loss/storage hardware durability.
- iPhone/iPad/Android install, local certificate trust, pass-and-hide, cache/reconnect, or offline
  companion networking; the necessary code does not exist.
- Interactive WPF visual appearance, screen-reader/high-contrast behavior, Windows lock/suspend
  timing, shoulder-surfing prevention, or operating-system screenshot behavior. XAML parsing/build
  and view-model tests do not prove these.
- Clean-machine self-contained installation with WAN disabled, audio/voice fallback, four-hour
  resource budgets, and every physical camera/GPU/Windows configuration promised by a release.
- Asset/branding distribution rights or a complete third-party redistribution notice inventory.

No distributable release or installer was packaged or published, and no commit or push was performed. A successful audit test
run validates the repaired implementation slice; it does not change the incomplete-product verdict.
